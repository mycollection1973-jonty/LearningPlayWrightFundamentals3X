01 Overview

Playwright is a client–server system, not a library that drives a browser directly. Your code talks to a driver, and the driver talks to a patched browser over a persistent connection.

Three ideas carry most of the architecture:

  • Two packages, two jobs. @playwright/test is the test runner (spec files, fixtures, workers, reporters). playwright is the browser automation library (launching browsers, creating contexts and pages). The runner is built on top of the library.
  • The browser is not in your process. Browsers always run as separate OS processes. Your test process holds a connection to them, so a browser crash does not take the test runner down with it.
  • Communication is stateful. One long-lived WebSocket carries commands out and events back — DOM changes, network requests, console logs, dialogs. That two-way channel is what makes auto-waiting and tracing possible.
The one-sentence version

Test code calls a client library, which sends messages to a driver, which translates them into a browser-specific protocol spoken by a patched browser engine running in its own process.

02 The three layers

Each layer has one job and a clear boundary with the next.

Layer 1 — Client libraries

The API you write tests against. Four official bindings exist: Node.js/TypeScript (the reference implementation), Python, Java, and .NET. A binding is a thin translation layer that serializes your calls into the Playwright protocol.

page.goto()locator.click()expect()

Layer 2 — Runner & driver

The runner schedules tests; the driver executes browser work. The driver holds the browser connections, applies auto-waiting, and routes events back to your test so waitForEvent() and page.on('request') work.

workersfixturesevent routing

Layer 3 — Browser engines

Not wrappers around installed browsers. Playwright ships its own patched builds of Chromium, Firefox, and WebKit — which is why it can offer identical behaviour and features across all three. You can point it at a system browser with channel instead.

chromiumfirefoxwebkitchannel: 'chrome'

Why patch the browsers?

Selenium depends on each vendor's own WebDriver. Playwright instead maintains patches so that Firefox and WebKit expose a protocol with the same capabilities as CDP. Consistent protocol ⇒ consistent behaviour across engines, and features land everywhere at once.

03 Protocols & transport

Two things are often conflated: the transport (WebSocket) and the protocol spoken over it (CDP, Juggler, WebKit).

Transport: one persistent connection

A WebSocket is opened once and kept open. Commands flow out as small frames; events flow back without being requested. Compare that with HTTP, where every action is a fresh request–response cycle.

Aspect Playwright HTTP / WebDriver style
Connection Persistent WebSocket New request per command
Direction Bidirectional — browser pushes events Client-initiated polling only
Per-command overhead Minimal frame header Handshake + headers each time
Waiting for the page React to events as they arrive Poll or sleep until state matches

Protocol: one per engine

Engine Protocol Notes
Chromium CDP Chrome DevTools Protocol — the same protocol DevTools uses. Playwright also exposes it directly: context.newCDPSession(page).
Firefox Juggler Playwright's own protocol, implemented by patches carried in the Firefox build it ships.
WebKit WebKit protocol A patched WebKit build exposing the inspector protocol Playwright needs.
Key consequence

Because the driver normalizes all three protocols into one API surface, the same test runs unchanged on every engine. That is why your playwright.config.ts can list three projects — Chromium, Firefox, WebKit — and the same spec file passes on all of them.

What a translated command looks like

A CDP command carries an id (to match the response), a method, and params:

// page.goto('https://example.com') becomes:
{
  "id": 1,
  "method": "Page.navigate",
  "params": { "url": "https://example.com" }
}

// the browser answers on the same socket:
{
  "id": 1,
  "result": { "frameId": "A1B2C3", "loaderId": "F6G7H8" }
}
Where the WebSocket runs

With the Node.js client, the driver runs in the same process, so there is no socket between your code and the driver — only between the driver and the browser. With the Python, Java, and .NET clients, the driver is a separate Node.js process reached over a WebSocket. That is why those languages still need Node.js installed.

04 Test runner model

The runner is a scheduler. Tests execute inside worker processes, which are separate OS processes that cannot see each other's memory.

Fixtures

Fixtures are the dependency-injection system behind the objects your test receives. You do not construct a page — you ask for it, and the runner builds it, hands it to you, and tears it down afterwards.

Scope Lifetime Typical members
worker Built once per worker process, shared by every test it runs browser, playwright, saved auth state
test Built fresh for each test, destroyed in reverse order afterwards context, page, request, custom fixtures
In this repo

tests/example.spec.ts only asks for page, so the runner supplies a fresh context and page per test — viewer and admin never share cookies or storage even though they run the same assertions.

Reporters

Reporters consume results as they are produced, and several can run at once. This project uses reporter: 'html', which writes to playwright-report/ and is opened with npx playwright show-report. Other common choices are list (live console output), json, junit, and blob (used to merge sharded runs).

Retries and traces

retries re-runs a failed test in a fresh context. Because the driver can record everything that crosses the protocol, a retry can also capture a trace — DOM snapshots, screenshots, network log, console output, and source — into a single trace.zip that you replay in the Trace Viewer.

// playwright.config.ts
use: {
  trace: 'on-first-retry',   // record only when a retry happens
  headless: false           // this repo runs headed by default
},
retries: process.env.CI ? 2 : 0

05 Browser, Context, Page

This hierarchy is the part you touch daily. Getting the cost model right explains why Playwright tests run in parallel so cheaply.

In this repo

tests/multiple_context.ts is exactly Figure 3: one chromium.launch(), then two browser.newContext() calls for an admin and a viewer, each with its own page. Compare with tests/normal_pw.ts, which walks the same chain once — browser → context → page — and closes them in reverse order.

// tests/multiple_context.ts — one browser, two isolated users
const browser = await chromium.launch({ headless: false });

const adminContext  = await browser.newContext();
const adminPage     = await adminContext.newPage();

const viewerContext = await browser.newContext();
const viewerPage    = await viewerContext.newPage();

// cleanup in reverse order of creation
await adminContext.close();
await viewerContext.close();
await browser.close();

Where the runner creates these for you

Under @playwright/test you rarely write the code above. The runner has already launched the browser (worker-scoped) and created a context and page (test-scoped) before your test function runs. Write the explicit chain only in standalone scripts, or when a single test needs additional contexts.

06 Lifecycle of a command

Tracing one await page.goto('https://playwright.dev/') from your spec file to the rendered page and back.

  1. Worker starts and the browser is launched The runner gives a worker process its first test. The worker-scoped browser fixture launches the engine as a separate OS process and opens the WebSocket driver connection.
  2. A context and page are created Test-scoped fixtures build an isolated BrowserContext and a default Page in it, so the test starts from a clean slate.
  3. Your call is serialized page.goto() leaves the client library as a protocol message and arrives at the driver — an in-process call for Node.js, a WebSocket hop for other languages.
  4. The driver translates it The API call becomes a browser-specific command (Page.navigate for CDP) and is written to the browser's WebSocket.
  5. The browser does the work Network requests fire, HTML parses, the DOM is built, styles and layout are computed, the page paints. This is where nearly all of the wall-clock time goes.
  6. Events stream back Rather than waiting for one reply, the driver watches the event stream — navigation committed, load fired, network idle. This is what goto() actually waits on, and why you rarely need a manual wait.
  7. Your code resumes The await resolves with a response object once the navigation is complete, and the next line of the test runs.
Why this matters

Steps 3–6 happen on a channel that is already open. There is no handshake, no per-command reconnect, and events arrive on their own — the three properties that make auto-waiting, network interception, and tracing practical.

07 Auto-waiting

Auto-waiting lives in the driver, not in your test. Before an action is performed, the element must pass a set of actionability checks — and the driver retries until it does or the timeout expires.

visible› stable› receives events› enabled› editable (fill only) → action is dispatched
Check What it means
VisibleRendered with a non-empty bounding box and not visibility: hidden.
StableThe bounding box is unchanged across two consecutive animation frames — nothing is sliding or fading underneath the pointer.
Receives eventsA hit-test at the element's centre point lands on the element itself, not on an overlay covering it.
EnabledNot a disabled control.
EditableNot readonly or disabled — only relevant for fill-style actions.

The same retry idea applies to assertions. Web-first assertions such as await expect(page).toHaveTitle(...) re-evaluate until they pass or hit the assertion timeout, which removes the need for sleeps.

Consequence

Manual waits fight the architecture. page.waitForTimeout(5000) does not make an action more reliable — it makes the suite slower and still fails when the element takes longer than the guess. If a test is flaky, the fix usually belongs in the locator.

08 Locators & selectors

A locator is not an element handle. It is a lazy description of how to find an element, re-resolved on every use.

  • Lazy resolution. A locator stores a query, not a DOM reference. Each action re-queries the page, so it cannot go stale between steps.
  • Retry-aware. Resolution and actionability checks are retried together until the timeout, so a locator can be declared before the element exists.
  • Composable. Locators can be filtered and chained — page.getByRole('row').filter({ hasText: 'Admin' }) — which keeps selectors readable as pages get complex.

Built-in selector engines

Engine Entry point Use it for
RolegetByRole()Preferred default — matches how the accessibility tree sees the page.
LabelgetByLabel()Form fields, matched by their visible label.
PlaceholdergetByPlaceholder()Inputs identified by placeholder text.
TextgetByText()Non-interactive content such as headings and paragraphs.
Test IDgetByTestId()Explicit hooks a team controls — stable and immune to copy changes.
CSS / XPathlocator()Escape hatch when nothing semantic identifies the element.
In this repo

tests/tta-check.spec.ts uses two of these flavours: getByRole('textbox', { name: 'Email Address' }) for the fields and getByTestId('login-button') for the button. That mix is the recommended pattern — semantic roles where the markup is meaningful, a test id to anchor the one element that matters most.

09 Glossary

The vocabulary, in the order you meet it.

Playwright Test
The test runner, shipped as @playwright/test. Discovers spec files, orchestrates workers, provides fixtures, retries failures, and produces reports. package.json → devDependencies
Playwright Library
The browser automation core, shipped as playwright. Exposes the browser APIs independently of any test runner — the reason a standalone script can drive a browser without a test framework. tests/normal_pw.ts
Driver / server
The translation layer between the client API and the browser's own protocol. Applies auto-waiting, routes events, and manages connections. In-process for Node.js clients, a separate Node.js process for other languages.
CDP
Chrome DevTools Protocol — the JSON command protocol used to control Chromium. The same protocol the browser's DevTools panel uses. Accessible directly via newCDPSession().
Juggler
Playwright's own automation protocol for Firefox, implemented by patches in the Firefox build Playwright ships.
BrowserType
The entry point for an engine — the chromium, firefox, and webkit objects. Offers launch(), launchPersistentContext(), connect(), and connectOverCDP().
Browser
A single running browser process. Expensive to create, so it is normally worker-scoped and shared by every test that worker runs. Can host many contexts. tests/normal_pw.ts → chromium.launch()
BrowserContext
An isolated, incognito-like profile inside a browser: its own cookies, storage, cache, and permissions. Cheap to create and the unit of test isolation. Tests in different contexts cannot affect each other. tests/multiple_context.ts
Page
A single tab or popup within a context. Where navigation, locators, and most interactions happen. tests/example.spec.ts → ({ page })
Frame
A browsing context inside a page — the main frame plus any <iframe>. Locators are resolved relative to a frame, which is why frame-based locators are scoped with frameLocator().
Locator
A lazy, re-resolved description of how to find an element, plus auto-waiting on every action. The successor to brittle element handles.
Selector engine
The strategy a locator uses to find elements — role, label, text, testid, css, xpath. Custom engines can be registered.
Actionability
The five checks (visible, stable, receives events, enabled, editable) an element must satisfy before an action is dispatched.
Web-first assertion
An assertion that retries until it passes or times out — expect(locator).toBeVisible() — instead of evaluating once.
Fixture
A dependency the runner sets up and tears down for you, scoped to a test or a worker. Built-ins include browser, context, page, and request. ({ page }) → injected by the runner
Worker
A separate OS process that runs tests. Each worker owns its browser instance and cannot share memory with other workers. Default count is half the available CPU cores. playwright.config.ts → workers
Project
A named configuration binding a set of options — browser, device, viewport — that specs run against. One spec on three projects means three executions. playwright.config.ts → projects
Sharding
Splitting the suite across machines with --shard=1/3. Complements workers, which parallelize within one machine.
Trace
A recording of a test run — DOM snapshots, screenshots, network, console, and source — saved as trace.zip and replayed in the Trace Viewer. playwright.config.ts → trace: 'on-first-retry'
Storage state
A serialized snapshot of cookies and localStorage saved to JSON and reused to skip logging in on every test.
Reporter
A consumer of test results — list, html, json, junit, blob. Several can run at once. playwright.config.ts → reporter: 'html'
Codegen
The recorder that watches your interactions and emits a runnable test, preferring role and test-id locators over raw CSS. npx playwright codegen
Headless
Running the browser with no visible window. This repo overrides the default with headless: false so you can watch tests execute. playwright.config.ts

11 Compared to Selenium

Most behavioural differences between the frameworks trace back to these architectural choices.

Aspect Playwright Selenium
Model Client → driver → browser, all out-of-process Client → WebDriver → browser
Transport Persistent WebSocket HTTP request per command
Protocol Playwright protocol over CDP / Juggler / WebKit W3C WebDriver
Browser control Patched engines shipped by the project Vendor-maintained drivers
Waiting Auto-waiting in the driver Explicit waits written by you
Isolation Browser contexts, created per test Separate browser sessions or profiles
Parallelism Built-in workers and sharding Selenium Grid, separate infrastructure
Recording Built-in traces with DOM snapshots External tooling
